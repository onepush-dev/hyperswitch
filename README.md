# Hyperswitch — open-source payments router (Juspay) with Control Center dashboard. Deploy on Railway with one click.

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/deploy/TEMPLATE_CODE)

[Hyperswitch](https://github.com/juspay/hyperswitch) is Juspay's open-source, Rust-based payments switch: one API in front of 100+ processors (Stripe, Adyen, Checkout.com, Braintree, PayPal, …) with smart routing, retries, vaulting, refunds, disputes, payouts and analytics. This template runs the **v1.128.0 router** (released 2026-10-16) and the **v1.38.10 Control Center** dashboard on Railway Postgres + Redis, with **zero deploy-time inputs** and **database migrations applied automatically** on every boot.

## Why this template
- **Latest release, digest-pinned:** router `v1.128.0` (official `juspaydotin/hyperswitch-router:v1.128.0-standalone` as the base) and Control Center `v1.38.10`. Postgres, Redis and every image are pinned by digest. Nothing uses `latest`. Other Hyperswitch templates on Railway are on older releases (router v1.123.x).
- **No Rust build at deploy time:** the router service is a ready image. `ghcr.io/onepush-dev/hyperswitch-router` is the official image plus three things, built by this repo's GitHub Actions workflow: the matching `v1.128.0` config, the `v1.128.0` migrations, and diesel CLI 2.3.5 (checksum-verified). Deploys take about a minute.
- **Migrations run themselves:** upstream's compose file uses a separate `migration_runner` container that installs diesel and runs `just migrate` against a source checkout. Here the router's entrypoint runs `diesel migration run` (and retries while Postgres starts up), then starts the router. Re-runs do nothing when the schema is already current.
- **Works without Superposition:** since v1.124 the router needs a Superposition config server. Upstream ships a seed file as an offline fallback, and this image points the router at that file. You don't need the extra Superposition service and its seeding job.
- **Secrets are unique per deploy:** admin API key, JWT secret, the 64-hex master encryption key, the API-key hash key and the user-auth-methods key are all generated by Railway. Upstream's sample values (`test_admin`, `secret`, …) are never used. No default user is created; you sign up yourself.
- **Small footprint:** router about 60–90 MB RAM with 2 workers, dashboard about 45 MB.

No start commands are needed for the router or the dashboard. The router image's ENTRYPOINT (`router/railway-entrypoint.sh`) does the following:
1. It maps `PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE` onto every database section the router reads (master, replica, accounts, global, analytics). Any `ROUTER__<SECTION>__*` variable you set wins.
2. It runs the migrations.
3. It chowns the volume and drops to the image's unprivileged `app` user.
4. It execs `/local/bin/router -f /local/config/hyperswitch.toml`.

Redis keeps Railway's default start command (`redis-server --requirepass $REDIS_PASSWORD --save 60 1 --dir $RAILWAY_VOLUME_MOUNT_PATH`).

## After deploy
1. Open the **control-center** URL and choose **Sign up**. The first account creates its own organization, merchant and profile. Email verification is off because no SMTP is configured. The dashboard offers TOTP 2FA, and you can skip it.
2. Add a processor under **Connectors**. To try things without any processor account, use the built-in **PhonyPay** test connector (`phonypay`).
3. Create an API key under **Developers → API Keys**, then call the router:
   ```bash
   curl -X POST https://<router-domain>/payments -H "api-key: $API_KEY" -H "Content-Type: application/json" -d '{
     "amount": 1000, "currency": "USD", "confirm": true, "profile_id": "<profile_id>",
     "authentication_type": "no_three_ds", "payment_method": "card", "payment_method_type": "credit",
     "payment_method_data": {"card": {"card_number": "4242424242424242", "card_exp_month": "10",
       "card_exp_year": "30", "card_holder_name": "Test", "card_cvc": "123"}}}'
   ```
4. Server-to-server admin calls (e.g. `/accounts`) use `ROUTER__SECRETS__ADMIN_API_KEY` as the `api-key` header. You can read it in the router's Variables tab.

Health: `GET /health` returns `health is good`. `GET /health/ready` reports database, redis and analytics status (router). `GET /health` on the dashboard returns `health is good`.

## Notes
- **Keep `ROUTER__SECRETS__MASTER_ENC_KEY` and `ROUTER__API_KEYS__HASH_KEY` forever.** Changing them makes encrypted merchant data unreadable and invalidates every API key. Back them up together with the Postgres volume.
- **Sandbox, not PCI:** cards are stored by the built-in **mock locker** in Postgres (`locker.mock_locker = true`), as in upstream's Docker setup. For production you need Juspay's card vault and the rest of upstream's production checklist.
- Not included (optional upstream services): the **scheduler** producer/consumer (needed for delayed jobs such as outgoing webhook retries, payment sync and API-key expiry reminders), the **drainer** (KV mode), the **Web SDK** / demo store, Kafka/ClickHouse/OpenSearch analytics, and mailhog/SMTP. The dashboard, signup and login, connectors, API keys and the payments API work without them.
- The dashboard's `sdk_url` still points at upstream's local default, so the dashboard's in-browser "test payment" checkout widget won't load. Use the API (above) or deploy `hyperswitch-web` yourself and set `default__endpoints__sdk_url` on control-center.
- Uploaded files (dispute evidence, theme assets) use upstream's `file_system` storage under `/local/bin/files`, which sits on a volume.
- Superposition: the router logs a `primary config fetch failed` warning at boot and once an hour. That's expected, because it is reading the bundled fallback seed.
- Upgrading: bump `HYPERSWITCH_VERSION` in the workflow and the base image tag and digest in `router/Dockerfile`, let CI publish, then point the service at the new digest. Migrations apply on the next boot. Back up Postgres first.
